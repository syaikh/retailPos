# Retail Product Form Integration Plan

## Executive Summary

Integrate comprehensive retail product form with 7 sections (Basic Info, Sales, Inventory, Supplier, Variants, Media, Settings) into current Go + PostgreSQL + SvelteKit system. Current system has minimal product fields; target is scalable architecture supporting both simple UMKM operations and enterprise features.

**Goal:** Seamless integration maintaining backward compatibility while adding advanced product management capabilities.

**Approach:** Phased implementation to minimize risk, starting with core extensions then adding complex features like variants and suppliers.

---

## Current System Analysis

### Existing Product Structure
**Database (`products` table):**
- id, sku, name, barcode, category_id, price, cost, stock, stock_min, stock_max, store_id, is_active
- created_at, updated_at, deleted_at

**Backend (Go):**
- Basic CRUD operations via ProductRepository
- Simple validation (name, sku, category, price required)
- Handler methods: CreateProduct, UpdateProduct, GetProducts, etc.

**Frontend (SvelteKit):**
- InventoryPage.svelte with basic modal form
- Fields: name, sku, barcode, category, price, stock, stock_min
- Simple table display with search/filter

**Limitations:**
- No brand/supplier tracking
- No product variants
- No media/images
- No advanced inventory (multi-warehouse, batch/expiry)
- No tax classes or units of measure

---

## Integration Strategy

### Architecture Decision: Normalized vs Extended
**Option 1: Extend products table** (simpler, faster)
- Add nullable columns to existing table
- Pro: Minimal migration complexity
- Con: Less scalable for complex variants/suppliers

**Option 2: Normalized design** (scalable, follows best practices)
- Separate tables for brands, suppliers, variants, images, inventory
- Pro: Enterprise-ready, clean data model
- Con: More complex migration and implementation

**Chosen Approach:** **Normalized design** with phased implementation. User emphasized scalability for large businesses while keeping simple for UMKM.

### Backward Compatibility
- Existing products remain functional
- New fields optional initially
- Graceful degradation for simple use cases

**New tables:**
```sql
-- Brands
CREATE TABLE brands (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE,
    description TEXT,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Tax classes
CREATE TABLE tax_classes (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE,
    rate_percent DECIMAL(5,2) NOT NULL,
    description TEXT,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Units of measure
CREATE TABLE units_of_measure (
    id SERIAL PRIMARY KEY,
    code VARCHAR(10) NOT NULL UNIQUE, -- pcs, box, kg, liter, etc.
    name VARCHAR(100) NOT NULL,
    description TEXT,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Warehouses (for multi-location inventory)
CREATE TABLE warehouses (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    code VARCHAR(20) UNIQUE NOT NULL,
    address TEXT,
    store_id INTEGER REFERENCES stores(id),
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### Phase 2: Supplier Relationships
```sql
-- Suppliers
CREATE TABLE suppliers (
    id SERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    code VARCHAR(50) UNIQUE,
    contact_person VARCHAR(100),
    email VARCHAR(100),
    phone VARCHAR(20),
    address TEXT,
    payment_terms VARCHAR(100), -- "Net 30", "COD", etc.
    lead_time_days INTEGER,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Product-Supplier relationships
CREATE TABLE product_suppliers (
    id SERIAL PRIMARY KEY,
    product_id INTEGER NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    supplier_id INTEGER NOT NULL REFERENCES suppliers(id) ON DELETE CASCADE,
    supplier_sku VARCHAR(50),
    is_primary BOOLEAN DEFAULT false,
    lead_time_days INTEGER,
    min_order_qty INTEGER DEFAULT 1,
    cost_price INTEGER NOT NULL, -- supplier's price to us
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(product_id, supplier_id)
);
```

### Phase 3: Product Variants
```sql
-- Variant attributes (color, size, flavor, etc.)
CREATE TABLE variant_attributes (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL, -- "Color", "Size", "Flavor"
    code VARCHAR(50) NOT NULL UNIQUE,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Variant values (Red, Blue, Small, Medium, etc.)
CREATE TABLE variant_values (
    id SERIAL PRIMARY KEY,
    attribute_id INTEGER NOT NULL REFERENCES variant_attributes(id) ON DELETE CASCADE,
    value VARCHAR(100) NOT NULL,
    code VARCHAR(50), -- Optional short code
    sort_order INTEGER DEFAULT 0,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(attribute_id, value)
);

-- Product variants
CREATE TABLE product_variants (
    id SERIAL PRIMARY KEY,
    product_id INTEGER NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    sku VARCHAR(50) UNIQUE,
    barcode VARCHAR(50) UNIQUE,
    variant_combinations JSONB NOT NULL, -- {"Color": "Red", "Size": "M"}
    price_adjustment INTEGER DEFAULT 0, -- additional cost over base price
    stock INTEGER DEFAULT 0,
    stock_min INTEGER DEFAULT 0,
    weight_grams INTEGER,
    dimensions_cm JSONB,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

### Phase 4: Media & Advanced Inventory
```sql
-- Product images
CREATE TABLE product_images (
    id SERIAL PRIMARY KEY,
    product_id INTEGER REFERENCES products(id) ON DELETE CASCADE,
    variant_id INTEGER REFERENCES product_variants(id) ON DELETE CASCADE,
    filename VARCHAR(255) NOT NULL,
    original_filename VARCHAR(255),
    url VARCHAR(500) NOT NULL,
    alt_text VARCHAR(255),
    sort_order INTEGER DEFAULT 0,
    is_primary BOOLEAN DEFAULT false,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    CHECK (product_id IS NOT NULL OR variant_id IS NOT NULL)
);

-- Advanced inventory tracking (replaces simple products.stock)
CREATE TABLE inventory (
    id SERIAL PRIMARY KEY,
    product_id INTEGER REFERENCES products(id) ON DELETE CASCADE,
    variant_id INTEGER REFERENCES product_variants(id) ON DELETE CASCADE,
    warehouse_id INTEGER NOT NULL REFERENCES warehouses(id),
    quantity INTEGER NOT NULL DEFAULT 0,
    reserved_quantity INTEGER DEFAULT 0, -- for pending orders
    incoming_quantity INTEGER DEFAULT 0, -- on order
    batch_number VARCHAR(100),
    expiry_date DATE,
    cost_price INTEGER, -- per unit cost for this batch
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(product_id, variant_id, warehouse_id, batch_number, expiry_date)
);
```

### Migration Strategy
1. **Phase 1 Migration:** Add columns to products table, create basic reference tables
2. **Data Migration:** Set default values for existing products
3. **Phase 2-4 Migrations:** Add complex tables as features are implemented
4. **Indexes:** Add performance indexes for new foreign keys and common queries
5. **Seed Data Updates:** Update existing seeders and add new seeders for reference data

## Migration Path & Data Compatibility

### Backward Compatibility Strategy
1. **Existing products:** All new fields nullable, default to NULL
2. **API responses:** Include new fields only if populated
3. **Form validation:** New fields optional initially
4. **Database queries:** Use LEFT JOINs for optional relationships

## Performance Considerations

### Database Performance
- **Indexes:** Add on foreign keys, common filter fields (brand_id, supplier_id, warehouse_id)
- **Query optimization:** Use appropriate JOINs, avoid N+1 queries
- **JSONB optimization:** For dimensions, variant_combinations - GIN indexes if needed

### API Performance
- **Pagination:** Implement for large result sets (brands, suppliers, variants)
- **Caching:** Cache reference data (brands, tax classes, UOM) in Redis if available
- **Lazy loading:** Load variants/images only when needed in detail views

### Frontend Performance
- **Component splitting:** Lazy load complex components (variant manager, image upload)
- **Virtual scrolling:** For large product lists
- **Image optimization:** Compress and resize uploaded images
