## Partitioning Strategy

### Raw Sales Table
- **Granularity**: Daily partitions (more practical than hourly)
- **Reason**: ~365/year vs ~8,760/year (hourly overhead too high)
- **Approach**: Range partitioning on `created_at`

### Aggregation Tables (NOT partitioned)
These are summary tables with pre-calculated metrics:
- `sales_hourly` - 24 rows/day/store (period aggregations)
- `sales_daily` - 365 rows/year/store  
- `sales_monthly` - 12 rows/year/store
- `sales_yearly` - 1 row/year/store

## Continuous Aggregates (TimescaleDB)

```sql
-- Hourly rollup - refreshes every hour
CREATE MATERIALIZED VIEW sales_hourly
WITH (timescaledb.continuous) AS
SELECT 
    store_id,
    time_bucket('1 hour', created_at) as bucket,
    SUM(total_amount) as revenue,
    COUNT(*) as orders,
    AVG(total_amount) as avg_order_value
FROM sales
GROUP BY store_id, bucket;

-- Daily rollup - base for other aggregations  
CREATE MATERIALIZED VIEW sales_daily
WITH (timescaledb.continuous) AS
SELECT 
    store_id,
    time_bucket('1 day', created_at) as bucket,
    SUM(total_amount) as revenue,
    COUNT(*) as orders
FROM sales
GROUP BY store_id, bucket;
```

## Notes

- Partition overhead: Each partition requires catalog entries and file descriptors
- Query patterns: Most queries filter by date ranges, not exact timestamps
- Store filtering: Add store_id to partition key if multi-store queries need optimization
