# Plan: Fix Timezone Database PostgreSQL untuk Operasional Indonesia

## Objective

1. Menyetel timezone database ke `Asia/Jakarta`
2. Mengidentifikasi dampak perubahan terhadap query yang sudah ada
3. Memperbaiki query agar konsisten, akurat, dan optimal performanya
4. Menetapkan best practice untuk handling waktu ke depan

---

## Step 1 — Ubah Timezone Database

### Opsi permanen (recommended):

```sql
ALTER SYSTEM SET timezone = 'Asia/Jakarta';
```

Restart container setelah perubahan.

### Alternatif (environment variable Podman):

```bash
-e TZ=Asia/Jakarta
```

### Verifikasi:

```sql
SHOW timezone;
SELECT CURRENT_DATE, NOW();
```

Expected:

- TimeZone = Asia/Jakarta
- CURRENT_DATE sesuai tanggal lokal

---

## Step 2 — Identifikasi Dampak

### 1. Perubahan hasil query berbasis tanggal

Query seperti:

```sql
created_at::date = CURRENT_DATE
```

akan menghasilkan data berbeda setelah timezone diubah.

**Impact:**

- Laporan harian bisa berubah (data bertambah/berkurang)
- Dashboard bisa "loncat hari"

### 2. Perubahan interpretasi data timestamp lama

Jika kolom menggunakan:

- `timestamp without time zone`

**Impact:**

- Data lama dianggap sebagai waktu lokal baru
- Bisa terjadi pergeseran waktu (logical shift)

### 3. Potensi bug pada fitur:

- Laporan harian
- Closing kasir
- Rekap shift
- Scheduled job (cron)

---

## Step 3 — Audit Struktur Kolom Waktu

Cek tipe data:

```sql
\d sales
```

### Jika menggunakan:

- `timestamp without time zone` ❌ (rawan bug)

### Rekomendasi:

- Gunakan `timestamptz` ✅

---

## Step 4 — Perbaikan Query (Best Practice)

### ❌ Hindari:

```sql
created_at::date = CURRENT_DATE
```

### ✅ Gunakan range query (index-friendly):

```sql
WHERE created_at >= date_trunc('day', now())
AND created_at < date_trunc('day', now()) + interval '1 day'
```

---

## Step 5 — Standarisasi Waktu (Best Practice)

### Opsi A (sistem lokal Indonesia):

- DB timezone: Asia/Jakarta
- Query langsung pakai CURRENT_DATE

### Opsi B (scalable / multi-region):

- Simpan data dalam UTC (`timestamptz`)
- Konversi di aplikasi (backend Go)
- Query pakai range dengan timezone explicit

## Step 4 — Perbaikan Query (Best Practice)

### Sebelum timezone diubah (DB UTC):

```go
// ❌ Tidak efisien - perlu offset manual
created_at >= CURRENT_DATE - INTERVAL '7 hours'
```

### Setelah timezone diubah (DB Asia/Jakarta):

```go
// ✅ Lebih sederhana dan akurat
created_at >= date_trunc('day', CURRENT_DATE)
```

### Query yang Perlu Diperbaiki:

**Line 44 (Today Sales):**
