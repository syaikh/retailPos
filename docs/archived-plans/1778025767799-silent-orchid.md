# Weekly & Monthly Revenue Report - Implementation Plan

## Overview
Add weekly and monthly revenue reporting capabilities to the retail POS system. Building on the existing daily revenue chart endpoint, this plan extends reporting to aggregate sales data at weekly and monthly granularities with multiple UI presentation options.

---

## Option 1: Multi-Tab Dashboard (Recommended)
A tabbed interface on the Reports page allowing users to switch between Daily, Weekly, and Monthly views.

### Backend Changes

#### File: `internal/delivery/http/handler/handler.go`
- Add `GetSalesWeeklyReport` handler
  - Aggregates sales by ISO week (Monday-Sunday)
  - Groups by `DATE_TRUNC('week', created_at)` 
  - Returns: `{ "week_start": "2026-05-04", "week_end": "2026-05-10", "total": 1500000, "order_count": 42 }`
- Add `GetSalesMonthlyReport` handler
  - Aggregates sales by calendar month
  - Groups by `DATE_TRUNC('month', created_at)`
  - Returns: `{ "month": "2026-05", "total": 4500000, "order_count": 128 }`
- Accept query params: `startDate`, `endDate`, `storeId` (optional)

#### File: `cmd/server/main.go`
- Add routes:
  - `GET /api/dashboard/chart/weekly` → `GetSalesWeeklyReport`
  - `GET /api/dashboard/chart/monthly` → `GetSalesMonthlyReport`

### Frontend Changes

#### File: `web/src/lib/pages/ReportsPage.svelte`
- Add tab state: `activeTab: 'daily' | 'weekly' | 'monthly'`
- Modify `fetchSales()` to also fetch weekly/monthly data when respective tab is active
- Replace line chart with dynamic chart that adapts to selected granularity:
  - **Daily**: Line chart with daily points (existing behavior)
  - **Weekly**: Bar chart showing weekly totals, x-axis shows week ranges (e.g., "May 4-10")
  - **Monthly**: Bar chart showing monthly totals, x-axis shows month names
- Add summary cards above the chart:
  - Total Revenue (selected period)
  - Total Orders
  - Average Order Value
  - % Change vs previous period

#### File: `web/src/lib/actions/chart.js`
- Enhance to support chart type switching (line ↔ bar)
- Add gradient fill variants for bars

Leverage existing frontend export infrastructure (`jspdf` + `jspdf-autotable` + `xlsx`):

- Use `xlsx` library already in `web/package.json`
- Export current view data as formatted Excel with multiple sheets:
  - Sheet 1: Summary (KPIs: total revenue, total orders, avg order value, % change)
  - Sheet 2: Raw data (date, revenue, order_count for each period)
- File name pattern: `revenue-report-{granularity}-{start}-to-{end}.xlsx`

### PDF Export  
- Use `jspdf` + `jspdf-autotable` (already in dependencies)
- PDF includes:
  - Header: Report title, date range, granularity
  - KPI summary in a formatted table
  - Chart image (rendered via HTML2Canvas or as data URL)
  - Detailed data table with pagination
- File name pattern: `revenue-report-{granularity}-{start}-to-{end}.pdf`

### Export Button Placement
- Position: Top-right corner of report card, next to date pickers
- Dropdown: [Excel] [PDF] icons (as existing export dropdown in ReportsPage)
- State: Disabled during data loading, shows spinner during generation
- Feedback: Toast notification on completion/failure

## Database Strategy: PostgreSQL 18 Aggregation

### Approach: Real-time Aggregation with Strategic Indexing

Given PostgreSQL 18 and the dataset scale (retail POS), **real-time aggregation with proper indexes** is the recommended approach over materialized views or aggregation tables because:

1. **Performance**: DATE_TRUNC queries on indexed `created_at` + `store_id` columns are extremely fast in PostgreSQL 18, even across millions of rows
2. **Data Freshness**: Sales data needs to be real-time (every new sale should reflect immediately in reports) - materialized views require refresh management
3. **Simplicity**: No need for complex refresh schedules, cache invalidation, or double-write logic to aggregation tables
4. **Maintenance**: Zero maintenance overhead vs managing materialized view refreshes or aggregation table ETL pipelines
5. **Flexibility**: Ad-hoc date ranges work naturally - no pre-computed buckets to constrain query patterns

### PostgreSQL 18 Optimizations

#### Index Strategy
```sql
-- Covering index for sales aggregation queries
CREATE INDEX idx_sales_aggregation 
ON sales (store_id, created_at DESC, total_amount) 
INCLUDE (id, invoice_number, cashier_id, status)
WHERE deleted_at IS NULL;

-- Partial index for active sales only (since soft-delete pattern is used)
CREATE INDEX idx_sales_active_aggregations 
ON sales (created_at DESC) 
WHERE deleted_at IS NULL AND status = 'completed';
```

#### Query Optimization (PostgreSQL 18 features)
```sql
-- Use generated columns for faster week/month lookups (computed once on write)
ALTER TABLE sales 
  ADD COLUMN week_bucket DATE GENERATED ALWAYS AS 
    (DATE_TRUNC('week', created_at)::date) STORED,
  ADD COLUMN month_bucket DATE GENERATED ALWAYS AS 
    (DATE_TRUNC('month', created_at)::date) STORED;

CREATE INDEX idx_sales_week_bucket ON sales (store_id, week_bucket) WHERE deleted_at IS NULL;
CREATE INDEX idx_sales_month_bucket ON sales (store_id, month_bucket) WHERE deleted_at IS NULL;
```

### When to Reconsider Materialized Views

Materialized views or aggregation tables become attractive if:
- Dataset grows > 100M rows and aggregation queries exceed 500ms
- Heavy concurrent reporting load (100+ simultaneous users running reports)
- Historical analysis on multi-year data with complex joins
- **Migration path**: Can add materialized views later without code changes - just swap the repository implementation

### Current Recommendation
**Start with real-time aggregation + covering indexes.** Monitor query performance with `EXPLAIN ANALYZE`. If weekly/monthly queries exceed 300ms consistently, then add generated columns for bucketing. If that's still insufficient, introduce targeted materialized views refreshed on sale completion (using the existing WebSocket event system to trigger refreshes).

### Performance Expectations (PostgreSQL 18)
- **Daily aggregation** (90 days): ~5-20ms with proper indexes
- **Weekly aggregation** (12 weeks): ~10-30ms  
- **Monthly aggregation** (24 months): ~15-40ms
- Even with 10M sales records: typically < 100ms for all aggregations

**Conclusion**: Use real-time queries for now, optimize with generated columns if needed, materialized views only as last resort.
