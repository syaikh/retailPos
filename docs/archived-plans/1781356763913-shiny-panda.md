# Plan: Sortable Users Table with Role & Status Filters

## Summary
Add sorting, role filtering, and status filtering to the UsersPage table with **server-side** support in the backend and **client-side** controls in the frontend. Uses Svelte 5 `$props()`, `$derived`, runes conventions, and the existing design system.

## Changes

### 1. Backend — Repository Interface (`internal/repository/repository.go`)

- Update `GetAllUsers` signature to accept `sortBy`, `sortDir`, `roleID`, and `isActive` params:
  ```go
  GetAllUsers(ctx context.Context, limit, offset int, search string, sortBy string, sortDir string, roleID int, isActive *bool) ([]domain.User, int, error)
  ```
- `*bool` for `isActive` allows three states: nil (all), true (active only), false (inactive only).
- `roleID` of 0 means all roles.

### 2. Backend — Repository Implementation (`internal/repository/postgres_repository.go`)

- Update `GetAllUsers` implementation:
  - **Filtering**: Add `role_id = $n` filter when `roleID > 0`. Add `is_active = $n` filter when `isActive != nil`. Apply filters to both COUNT and SELECT queries using the same parameterized `$n` pattern as `GetAllProducts`.
  - **Sorting**: Validate `sortBy` against a whitelist (`id`, `username`, `email`, `role_id`, `is_active`, `created_at`, `last_login`, `updated_at`) to prevent SQL injection. Default to `id` if invalid/empty. Validate `sortDir` is `asc` or `desc` (default `desc`). Append `ORDER BY <sortBy> <sortDir>` before LIMIT/OFFSET.
  - Increment `$n` parameter indices after adding each filter condition, same pattern as existing code.

### 3. Backend — Handler (`internal/delivery/http/handler/handler.go`)

- Update `ListUsers` to parse new query params:
  - `sort` → `sortBy` (string, validated by repo whitelist)
  - `dir` → `sortDir` (string, `asc`/`desc`)
  - `role` → `roleID` (int, 0 = all)
  - `status` → `isActive` (`"true"`, `"false"`, or empty for all; convert to `*bool`)
- Pass new params to `h.authRepo.GetAllUsers(...)`.
- `search` param unchanged.

### 4. Backend — Repository Tests (`internal/repository/repository_test.go`)

- Update existing test calls to `GetAllUsers` to include the new params.
- Add test cases: filter by role, filter by active status, filter by inactive status, sort by username asc, sort by email desc.

### 5. Frontend — `web/src/lib/pages/admin/UsersPage.svelte`

**Sorting:**
- Add `$state` vars: `sortBy` (string, default `'id'`) and `sortDir` ('asc' | 'desc', default 'desc').
- Make table headers clickable (User → `username`, Role → `role_id`, Status → `is_active`, Last Login → `last_login`).
- Sort indicators: `ChevronUp`/`ChevronDown` icons from lucide-svelte. Show active direction on sorted column, muted inactive chevrons on unsorted columns.
- Clicking a header sets `sortBy` to that column and toggles `sortDir` if already sorted by that column.
- Column widths maintained via explicit `min-width` style on `<th>` elements (User: 250px, Role: 120px, Status: 110px, Last Login: 200px, Actions: 100px).
- Sorting is server-side: changing sort triggers `fetchUsers()` with the new params.

**Filters (Role + Status):**
- Add `$state` vars: `filterRole` (string, default `'all'`) and `filterStatus` (string, default `'all'`).
- Place filter UI in the card header bar below the search bar, above the table:
  - Row 1: Role chips — "All Roles" + one chip per role from `roles` data
  - Row 2: Status chips — "All", "Active", "Inactive"
- Use `FilterChip` component from `$lib/components/ui/FilterChip.svelte`.
- Active chip uses primary styling (matching FilterChip active state).
- Filters are server-side: changing a filter resets `offset` to 0 and triggers `fetchUsers()`.
- When filters are active, show "Showing X of Y users" where Y = `total` from API (already server-filtered).
- Add a "Clear all filters" button (using `X` icon from lucide-svelte) when any filter or sort is active.

**API call updates:**
- `fetchUsers` sends `sort`, `dir`, `role`, `status` params alongside existing `search`, `limit`, `offset`.
- Update `Pagination` to use `total` from API response (already correct behavior).

**Data flow (server-driven):**
1. User types search → debounced `fetchUsers()` with search param
2. User clicks sort header → `fetchUsers()` with sort/dir params → server returns sorted data
3. User clicks role/status filter → reset offset → `fetchUsers()` with role/status params → server returns filtered data
4. Pagination works on the filtered/sorted server-side result set

**Svelte 5 conventions:**
- Use `$state` for sortBy, sortDir, filterRole, filterStatus
- Use `$derived` for `activeFilterCount`, `isFiltered`
- Event handlers use `onclick` (not `on:click`)
- No comments in code

**Imports to add:**
- `ChevronUp`, `ChevronDown`, `ArrowUpDown` from lucide-svelte
- `FilterChip` from `$lib/components/ui/FilterChip.svelte`

**No changes to:**
- Modal forms (add/edit/delete)
- Pagination component
- FilterChip component (used as-is)
- Backend test structure (only add params + test cases)
