**Dot-notation (legacy/alias):** `dashboard.view`, `user.view`, `user.create`, `user.update`, `user.delete`, `role.view`, `role.create`, `role.update`, `role.delete`, `product.view`, `product.create`, `product.update`, `product.delete`, `category.view`, `category.create`, `sale.view`, `sale.create`, `sale.print`, `report.view`, `audit.view`

**Redundant aliases:** `users:read` = `user:read`, `users:manage` = `user:manage` = `user:manage`, `users:roles:manage`, `reports:read` = `report:view`

### Key Problems
1. **No backend permission enforcement** — `RequirePermission()`, `AdminOnly()`, `RoleMiddleware()` exist in middleware but are NOT used on any route. All admin endpoints rely solely on `AuthMiddleware()` (token valid = access granted).
2. **Duplicate permissions** — 8 alias permissions create confusion and bloat.
3. **superadmin = admin** — Both have identical permissions. No distinction.
4. **staff has no permissions** — Staff Gudang role exists but can't do anything.
5. **Inconsistent naming** — Mix of `:` (colon) and `.` (dot) notation.
6. **Missing permissions** — No `sale:void`/`sale:refund`, no `product:export`, no `user:view` (single user detail).
7. **Frontend-only RBAC** — Sidebar hides admin section for cashier/staff, but API endpoints are still accessible directly.

## Impact & Risk Analysis

### High Risk
- **Permission seed data change** — Existing installations need migration `012` to clean up old permissions. Must be backward-compatible during transition.
- **Adding middleware to routes** — Could break existing API clients if permissions aren't correctly mapped. Mitigation: Test with all 5 roles before deploying.

### Medium Risk
- **Frontend sidebar changes** — Cashier currently sees Inventory/Reports/Categories. Removing these is intentional (least-privilege). Mitigation: Add redirect to Dashboard if user navigates to a hidden page directly via URL.
- **Admin losing audit access** — Currently admin has audit:read. Removing it enforces superadmin-only audit trail access. Mitigation: If admin users need audit visibility, add a read-only "Audit Viewer" role later.
- **Manager gaining write permissions** — Adding `product:update` and `sale:void` to manager expands their capabilities beyond current read-only. Mitigation: Verify with business requirements before implementation.

### Low Risk
- **Removing dot-notation permissions** — These are seed data, not referenced in code logic. Safe to remove.
- **Adding new permissions** — New permissions (`sale:void`, `product:export`, etc.) are additive only.
