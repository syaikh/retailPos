# Implementation Plan: Master Data Separation & Additions

## Overview

Three phases:
- **Phase 0**: Separate stock from product master data (`product_stock` table)
- **Phase 1**: Add `payment_methods` master data (replace hardcoded POS array)
- **Phase 2**: Add `customers` master data (enable CRM, receipts, future loyalty)

Each phase is independently deployable.

---

## Phase 0: Separate Stock from Product Master Data

### Goal
Split the current `products` table so `products` holds only catalog master data and `product_stock` holds inventory/stock data.

### Migration
File: `database/migrations/014_split_stock_to_product_stock.sql`
- Create `product_stock` table with: `id`, `product_id` (FK), `warehouse_id` (FK, nullable), `store_id` (FK, nullable), `quantity`, `reorder_point`, `reorder_quantity`, `last_restocked_at`, timestamps. Unique constraint on `(product_id, warehouse_id)` and `(product_id, store_id)`.
- Backfill from `products`: `INSERT INTO product_stock (product_id, store_id, quantity, created_at, updated_at) SELECT id, store_id, stock, created_at, updated_at FROM products`
- Create view `v_products_full` that LEFT JOINs `products` with `product_stock` so existing SELECT queries keep working.
- Add indexes on `product_stock` (product_id, warehouse_id, store_id).

### Backend Changes

**Domain** (`internal/domain/product_stock.go`): New `ProductStock` struct with fields matching the table.

**Repository interface** (`internal/repository/repository.go`):
- Add `ProductStockRepository` interface with: `GetStock`, `GetAllStock`, `AdjustStock`, `UpsertStock`.

**Repository impl** (`internal/repository/postgres_repository.go`):
- Add `ProductStock` to the single struct (no new file — the existing `postgresRepository` implements all interfaces).
- **Shadow-write strategy**: for the first iteration, update BOTH `products.stock` AND `product_stock.quantity` on every sale/adjustment. This keeps the view and any direct column reads working. Drop the shadow write only after all reads are fully migrated to the view.
- Update `CreateSale` (line ~1104): add `UPDATE product_stock SET quantity = quantity - $1 WHERE product_id = $2 AND (warehouse_id = $3 OR store_id = $3)`. If no row exists, insert one atomically in the same transaction. Also keep the existing `UPDATE products SET stock = stock - $1` for shadow-write.
- Update `AdjustStock` (line ~1824): same — write to `product_stock` AND keep `products.stock` update for shadow-write.
- Change `GetAllProducts` / `GetProductByID` / product detail query to read from `v_products_full` view instead of `products` table directly. The view must expose columns `stock`, `store_id`, `store_name` so existing callers need zero changes.
- RestoreProduct needs to clear the stock in the `product_stock` row during restore (if row exists).

**WebSocket broadcasts** (`internal/delivery/websocket/handler.go`):
- `BroadcastStockUpdate` must read the new quantity from `product_stock` (or use the already-updated value passed from the sale handler), but the JSON payload must keep the shape `{id, stock, name, ...}` so frontend handlers don't break.
- `BroadcastLowStockAlert` payload shape unchanged.

**Handler** (`internal/delivery/http/handler/handler.go`):
- `AdjustStock` handler: update audit log to accept both old and new paths. During shadow-write, `oldStock` can come from either `products.stock` or `product_stock.quantity`. After shadow-write is removed, read from `product_stock`.

**Routes** (`cmd/server/main.go`):
- No new routes in Phase 0. Existing routes automatically use the view.

**Seeder** (`cmd/seeder/main.go`, `database/seeds/012_product_stock.sql`):
- New seed file to populate `product_stock` after products are seeded.
- Modify `verifySeedData` to also count `product_stock` rows.

**Optional later cleanup** (not part of initial Phase 0 PR):
- Add `public.GET("/product-stock/:id", ...)` if you want a dedicated stock endpoint for the frontend to poll.
- Remove `stock` from the product create/edit form in InventoryPage to prevent dual-write confusion.

### Frontend Changes
- No changes needed in Phase 0 because the view returns the same `stock` field the frontend already reads.

### E2E Tests (Playwright)

**New / updated specs:**
- `tests/e2e/inventory-adjust-stock.spec.ts` — after adjustment, verify `GET /api/products/{id}` returns updated `stock` (still works via `v_products_full`); also verify `GET /api/product-stock/{id}` returns same quantity.
- `tests/e2e/pos-flow.spec.ts` — existing sale creation test must still pass. Add assertion that `stock` decreases by the sold quantity (via product endpoint).
- `tests/e2e/dashboard-live.spec.ts` — low-stock alert broadcast after a sale must still work (reads stock from product, which is now from the view).

**Test-and-fix loop for Phase 0:**
1. Run `npx playwright test tests/e2e/inventory-adjust-stock.spec.ts tests/e2e/pos-flow.spec.ts tests/e2e/dashboard-live.spec.ts` after code changes.
2. If tests fail because the view doesn't expose `stock` or the column is missing, fix the view definition or repository query before proceeding.
3. If AdjustStock handler audit log references `products.Stock` (no longer exists), fix the handler to read from `product_stock`.

## Phase 1: Add `payment_methods` Master Data

### Goal
Replace the hardcoded payment method array in `PosPage.svelte` with a central lookup table. Standardize `sales.payment_method` to use stable codes instead of free-text.

### Migration
File: `database/migrations/015_payment_methods.sql`
- Create `payment_methods` table: `id`, `code` (unique, e.g. `'CASH'`), `name` (display label), `is_active`, `requires_reference` (whether a card auth / e-wallet reference number is collected), `sort_order`, timestamps.
- Seed 5 rows: Cash, Card, E-Wallet, Transfer, QRIS.
- Alter `sales.payment_method` from `VARCHAR(50)` to `VARCHAR(30)` (store the `code`, not the display name). Existing seed data in `cmd/dummy/daily.go` and `cmd/dummy/main.go` inserts free-text values — these must be updated to codes (`'Cash'` → `'CASH'`).

**Seeder** (`database/seeds/012_payment_methods.sql`):
- Seed the master rows with `ON CONFLICT (code) DO NOTHING`.

### Backend Changes

**Domain** (`internal/domain/`):
- New `PaymentMethod` struct: `ID`, `Code`, `Name`, `IsActive`, `RequiresReference`, `SortOrder`, `CreatedAt`.

**Repository interface** (`internal/repository/repository.go`):
- Add `PaymentMethodRepository` interface with: `GetAllActive`, `GetByCode`, `GetByID`.

**Repository impl** (`internal/repository/postgres_repository.go`):
- Add methods: `GetAllPaymentMethods`, `GetPaymentMethodByCode`, `GetPaymentMethodByID`.

**Handler** (`internal/delivery/http/handler/handler.go`):
- `ListPaymentMethods(c *gin.Context)` — public endpoint, returns all active payment methods.
- `GetPaymentMethodByCode(c *gin.Context)` — optional, if frontend needs single lookup.

**Routes** (`cmd/server/main.go`):
- Add `public.GET("/payment-methods", h.ListPaymentMethods)`.

**Dummy data** (`cmd/dummy/daily.go`, `cmd/dummy/main.go`):
- Update any hardcoded `payment_method: 'Cash'` values to `payment_method: 'CASH'` (and similar for other methods).

### Frontend Changes

**Types** (`web/src/lib/types.ts`):
```ts
export interface PaymentMethod {
  id: number;
  code: string;
  name: string;
  requires_reference?: boolean;
  sort_order?: number;
}
```

**PosPage.svelte** (`web/src/lib/pages/PosPage.svelte`):
- Remove the hardcoded `paymentOptions` array (lines ~36-40).
- Add `let paymentMethods = $state<PaymentMethod[]>([])`.
- In `onMount`, fetch `/api/payment-methods` and populate the array.
- Replace the payment-method selector rendering to iterate over `paymentMethods`.
- Collect `requires_reference` field as needed (add reference number input when true).
- Update the sale POST payload: continue sending `payment_method` as the `code` string (frontend already sends a string, the API handler will accept codes).

**ReportsPage.svelte** (`web/src/lib/pages/ReportsPage.svelte`):
- `getPaymentMethodVariant` currently has a long chain of string `.includes()` checks. Replace with a lookup built from the `paymentMethods` list fetched on mount. Map `code` to variant: `CASH` → `success`, `CARD` → `primary`, `E_WALLET`/`QRIS` → `default`, `TRANSFER` → `muted`.

### E2E Tests (Playwright)

**New spec:** `tests/e2e/payment-methods.spec.ts`
- `GET /api/payment-methods` returns active list with expected codes (`CASH`, `CARD`, `E_WALLET`, `TRANSFER`, `QRIS`).
- POS page (`/pos`) loads and populates payment method buttons from API (not hardcoded).
- Creating a sale with each payment method code succeeds.
- Reports page renders payment method badges using the lookup table (no broken `getPaymentMethodVariant` output).

**Updated spec:** `tests/e2e/pos-flow.spec.ts`
- Payment method assertion: after mount, at least one payment button matches the API label (e.g. "Tunai"). Remove any assertion tied to hardcoded `'cash'` label; assert against `payment_methods.code` instead.

**Test-and-fix loop for Phase 1:**
1. Run `npx playwright test tests/e2e/payment-methods.spec.ts tests/e2e/pos-flow.spec.ts`.
2. If POS page still shows hardcoded buttons (old array not removed), fix PosPage.svelte to clear the fallback array before fetch.
3. If sale fails because backend rejects lowercase `'cash'` instead of `'CASH'`, fix dummy data seeds or normalize in handler.
4. If ReportsPage badge colors break, fix `getPaymentMethodVariant` to use the lookup map.

## Phase 2: Add `customers` Master Data

### Goal
Enable customer tracking on sales, receipt personalization, and a foundation for loyalty/CRM.

### Migration
File: `database/migrations/016_customers.sql`
- Create `customers` table: `id`, `name` (required), `phone` (unique, nullable), `email`, `address`, `tax_id` (NPWP), `loyalty_points` (default 0), `total_spent` (default 0, denormalized), `last_purchase_at`, `note`, `is_active` (default true), `is_walk_in` (default false), timestamps.
- Add indexes on `phone`, `is_active`.
- Seed a default walk-in customer (id=1, name='Pelanggan Umum / Walk-in') so existing sales can FK without migration.
- Add `customer_id INTEGER DEFAULT 1` to `sales`, FK to `customers(id)`.

### Backend Changes

## Execution Order & Dependencies

| Phase | Depends on | Risk | Value | E2E Gate |
|-------|-----------|------|-------|----------|
| 0 (product_stock) | None | Medium (changes all stock writes) | Foundation for multi-store stock | `inventory-adjust-stock`, `pos-flow`, `dashboard-live` |
| 1 (payment_methods) | None | Low | Removes hardcoded array; centralizes config | `payment-methods` (new), `pos-flow` |
| 2 (customers) | None | Medium (new UI page + sale FK) | Enables CRM, better receipts | `customers` (new), `pos-flow` |

Recommended: **Phase 0 + 1 first** (they touch the same write paths), then **Phase 2** later. Phases 0 and 1 can be done in a single PR if desired; Phase 2 should be separate because it introduces new UI and new sale FK logic. **Do not proceed to the next phase until all E2E tests for the current phase pass.**

## Testing Strategy

Each phase includes Playwright E2E tests. Run the full suite after implementing a phase, fix any failures, and only then move to the next phase.

### Per-Phase Test Commands

```bash
# Phase 0 — stock separation
npx playwright test tests/e2e/inventory-adjust-stock.spec.ts tests/e2e/pos-flow.spec.ts tests/e2e/dashboard-live.spec.ts

# Phase 1 — payment methods
npx playwright test tests/e2e/payment-methods.spec.ts tests/e2e/pos-flow.spec.ts

# Phase 2 — customers
npx playwright test tests/e2e/customers.spec.ts tests/e2e/pos-flow.spec.ts
```

### Regression Guard

After each phase, also run:
```bash
go test ./...
npx playwright test
```

### Bug Fix Loop

1. **Run focused E2E tests** for the current phase.
2. **Collect failures** — common expected fixes per phase:
   - **Phase 0**: `products.stock` column missing in view, `AdjustStock` handler referencing deleted column, `product_stock` row not inserted on first sale for a product.
   - **Phase 1**: POS still shows hardcoded buttons, sale rejects lowercase payment method codes, ReportsPage `getPaymentMethodVariant` returns `undefined` for codes not matched by old string checks.
   - **Phase 2**: `CreateSale` errors when `customer_id` omitted, sidebar hides Customers for manager, `sale.data` missing customer fields.
3. **Fix in place** — edit backend handler/repository or frontend component, then re-run only the failing spec.
4. **Re-run full phase spec set** to confirm.
5. **Re-run full E2E regression** (`npx playwright test`) before merging.

### Test Data Considerations

- All E2E tests against live API at `API_BASE` (default `http://localhost:9095`). Ensure `./seed-dev.sh` has been run with the new migration + seed files.
- Adjust stock tests revert changes at the end of each test.
- New payment method and customer seeds must be idempotent (`ON CONFLICT DO NOTHING`) so re-running `seed-dev.sh` doesn't fail.
- The existing `pos-flow.spec.ts` creates real sales; keep test product IDs stable or search by SKU to avoid brittle assertions.

## Rollback Strategy

Each phase is reversible via SQL:
- Phase 0: Drop `product_stock`, re-add `stock` column to `products`, drop view.
- Phase 1: Revert `sales.payment_method` type change; re-hardcode array in frontend (or store old strings).
- Phase 2: Drop `customers` table, remove `customer_id` from `sales`.

Because migrations are additive (no DROP in Phase 1/2), and development data is disposable, the main risk during Phase 0 is handled by the `v_products_full` view keeping reads compatible while writes are redirected.
