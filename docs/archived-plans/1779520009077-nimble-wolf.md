# Timezone Fix Plan for Retail POS System

## Problem Statement
The application uses TIMESTAMPTZ columns in PostgreSQL (storing UTC internally) but has inconsistent timezone handling:
1. Database session timezone is not explicitly set to Asia/Jakarta in the main application (only in seeder tools)
2. NOW() function in SQL queries uses the session timezone, leading to potential incorrect timestamps
3. Inconsistent timezone parsing between different parts of the codebase
4. The audit log generation uses local time without timezone conversion

## Root Cause
- Missing `timezone=Asia/Jakarta` parameter in database connection string for main application
- Some code uses `time.Now()` without converting to Jakarta timezone
- Inconsistent use of `time.LoadLocation("Asia/Jakarta")` vs `time.FixedZone`
- Missing explicit timezone handling in audit log timestamp generation

## Solution Overview
1. Ensure all database connections use Asia/Jakarta timezone via DSN parameter
2. Standardize timezone parsing using `time.LoadLocation("Asia/Jakarta")`
3. Update NOW() usage to be timezone-aware or rely on correct session timezone
4. Fix audit log timestamp generation to use Jakarta timezone
5. Update seeder tools to use consistent timezone handling
